## Требования

Docker с поддержкой Docker Compose.

## Развертывание микросервисов

1. Получение `git clone -b sprint-11 https://github.com/TuringMac/EventPlatform`
2. Сборка выполняется внутри контейнера  

3. Запуск сервисов со сборкой контейнеров из исходного кода осуществляется командой `docker compose up -d --build`. Первый пользователь с ролью Admin инициализируется с параметрами из конфигурации (Admin:Username).  

| Сервис | API | Swagger |
| --- | --- | --- |
| Users | http://localhost:5001 | http://localhost:5001/swagger |
| Events | http://localhost:5002 | http://localhost:5002/swagger |
| Bookings | http://localhost:5003 | http://localhost:5003/swagger |

4. Остановка сервисов с очисткой volumes выполняется командой `docker compose down -v`.  

Задано Development окружение, чтобы сохранить работоспособность Swagger для удобства тестирования.  

## Роли и авторизация

- Без токена доступны просмотр мероприятий (`GET /api/events`, `GET /api/events/{id}`), проверка состояния (`GET /api/health`), регистрация (`POST /api/auth/register`) и вход (`POST /api/auth/login`). Остальные маршруты API требуют JWT: без него возвращается 401, при недостаточных правах — 403.
- `User` может бронировать мероприятие (`POST /api/events/{eventId}/book`), просматривать свою бронь (`GET /api/bookings/{id}`) и отменять свою бронь через `DELETE /api/events/{eventId}/book`. Чужие брони ему недоступны.
- `Admin` также может создавать, изменять и удалять мероприятия (`POST`, `PUT`, `DELETE /api/events`), просматривать все брони мероприятия и пользователей, управлять пользователями и отменять любую бронь по `DELETE /api/bookings/{bookingId}`.
- Публичная регистрация создаёт пользователя с выбранной ролью, например `User`. Учётная запись `Admin` создаётся при инициализации базы из настроек `Admin:Username` и `Admin:Password` (в `appsettings.Development.json` указаны значения для локальной разработки).

### Получение JWT через Swagger

1. Запустите API согласно инструкции [Развертывание микросервисов](#развертывание-микросервисов).
2. При необходимости выполните `POST /api/auth/register` с JSON-полями `login` и `password`, чтобы создать пользователя с ролью `User`. Для входа как `Admin` используйте учётные данные из настроек `Admin`.
3. Выполните `POST /api/auth/login` с теми же `login` и `password`. Скопируйте значение `token` из ответа.
4. Нажмите **Authorize**, вставьте токен **без** префикса `Bearer` и подтвердите. Теперь можно вызывать защищённые маршруты; для смены роли войдите под другой учётной записью и повторите авторизациюс другим JWT.

### Конфигурация JWT

Параметры задаются в секции `Jwt`: `Issuer` (издатель), `Audience` (аудитория), `Key` (секрет подписи) и `Lifetime` (время жизни токена в минутах). Для локальной разработки `Issuer`, `Audience` и `Key` указаны в `EventPlatform/EventPlatform.Api/appsettings.Development.json`, а `Lifetime` (15 минут) — в `appsettings.json`. Для продакшна задайте собственный длинный случайный секрет `Jwt:Key` через переменную окружения `Jwt__Key` или защищённое хранилище секретов, а не храните его в репозитории; также настройте `Jwt:Issuer` и `Jwt:Audience` для своего окружения.  
Для каждого микросервиса должен быть задан одинаковый secret, чтобы использовать JWT между ними.

## Логика

### BookingBackgroundService

1. Сервис получает запрос от пользователя на создание брони и добавляет запись в БД
2. Далее публикует соответствующее сообщение в свой топик `bookings`
3. Bookings подписан на топик `events` и получит сообщение об успешности резервации мест
4. В зависимости от ответа бронь будет переведена в статус Confirmed или Rejected

### EventBackgroundService

1. Сервис подписан на топик `bookings` и ожидает сообщений
2. При получении сообщения от Bookings начинается процесс проверки мероприятия. А именно, дата проведения и число свободных мест.
3. При всех успешных проверках происходит резервация мест с записью в БД и публикация соответствующего сообщения в свой топик `events`

### Сценарии использования

#### Бронирование на мероприятие

1. Пользователь выбирает мероприятие
2. Запрашивает бронь на это мероприятие
3. Место резервируется
4. Ожидает подтверждения или отказа в бронировании
5. Во втором случае место освобождается

### Репозиторный слой

Доступ к данным инкапсулирован в репозиториях `EventRepository` и `BookingRepository`. Репозитории реализуют интерфейсы `IEventRepository` и `IBookingRepository`, используют `AppDbContext`, а бизнес-логика взаимодействует с ними через эти интерфейсы.

Интеграционные тесты проверяют репозитории на реальном PostgreSQL. Для этого используется Testcontainers: перед запуском тестов автоматически создается и запускается контейнер PostgreSQL, после чего применяются миграции базы данных. Для работы Testcontainers во время выполнения `dotnet test` должен быть запущен Docker.

### Кеширование

Redis используется как необязательный распределённый кеш для чтения мероприятия по идентификатору и получения топ-10. Это позволяет повторно использовать данные, снижая число обращений к БД и повторных вычислений рейтинга. БД остаётся источником истины; Redis хранит временные копии данных. Произвольные выборки с фильтрами и пагинацией не кешируются: это позволяет не усложнять формирование ключей и инвалидирование множества комбинаций запросов.  

`EventCachedRepository` реализует `IEventRepository` и оборачивает `EventRepository`. При чтении он:

1. Проверяет наличие данных в Redis.
2. При попадании возвращает данные из кеша.
3. При промахе обращается к репозиторию БД, сохраняет полученные данные в Redis с TTL и возвращает результат.

Для `EventService` это Read-Through: загрузка и заполнение кеша скрыты за обычным интерфейсом репозитория. Внутри декоратора применяется Cache-Aside: именно код приложения, а не Redis, загружает данные из БД при промахе.

Такой подход выбран по следующим причинам:

- Бизнес-сервис не управляет Redis, ключами и сроками хранения; код работы с БД не дублируется в кеширующей реализации.
- В тестах `EventService` достаточно замокать `IEventRepository`. Попадания, промахи и недоступность Redis проверяются отдельно в тестах декоратора.
- Кеширование можно отключить, зарегистрировав в DI обычный `EventRepository`, без изменения бизнес-сервиса.
- Методы, которым кеш не нужен, декоратор делегирует исходному репозиторию.

При создании или изменении мероприятия сначала сохраняются данные в БД, затем актуальный объект целиком записывается в Redis (Update-on-Write). При удалении мероприятия после успешной операции в БД удаляется соответствующий ключ кеша.

Обновление кеша вместо простого удаления ключа позволяет следующему читателю получить объект без дополнительного обращения к БД. Это полезно для часто просматриваемых мероприятий. При этом изменения включают не только редактирование описания, но и резервирование и освобождение мест, поэтому считать все записи редкими нельзя.

Сроки хранения задаются в настройках `Cache`:

- `RegularTTL` — для отдельного мероприятия, по умолчанию в конфигурации 5 минут;
- `Top10TTL` — для списка топ-10, по умолчанию в конфигурации 30 минут.

TTL позволяет ключам истекать даже при неудачном обновлении или удалении кеша и ограничивает срок хранения устаревших копий. Список топ-10 является отдельным снимком: изменение мероприятия не пересчитывает уже закешированный рейтинг. После истечения TTL он будет сформирован заново при следующем чтении.

Кеш закончившихся мероприятий инвалидируется автоматически по TTL и не будет бесконтрольно занимать память маловостребованными данными.

Подключение настроено с `AbortOnConnectFail = false`, политикой `BacklogPolicy.FailFast` и ограниченными тайм-аутами. Ошибки подключения и тайм-ауты операций кеша логируются: чтение продолжает работу напрямую через БД, а ошибка обновления кеша не отменяет успешную запись в БД. После восстановления связи клиент Redis может переподключиться без перезапуска сервиса.

Мероприятие хранится как JSON в ключе `event:{id}`, топ-10 — как JSON-массив в ключе `top10_events`. Приложение читает и заменяет эти значения целиком, не использует поиск или обновление отдельных полей средствами Redis. Поэтому String соответствует текущему способу доступа и упрощает сериализацию, замену значения одной командой и назначение TTL.

## Структура проекта

Проект разделен на три независимых сервиса с сохранением Clean architecture и принципами DRY.

### EventPlatform.Domain

Ядро предметной области. Содержит сущности `Event` и `Booking`, перечисления, доменные исключения и базовые доменные интерфейсы. Этот слой не знает о базе данных, ASP.NET Core, инфраструктуре или способе доставки запросов.

### EventPlatform.Application

Слой сценариев использования и бизнес-логики приложения. Содержит:

- интерфейсы сервисов и репозиториев;
- сервисы мероприятий и бронирований;
- DTO для обмена данными с API;
- `BookingBackgroundService`, который периодически обрабатывает ожидающие бронирования.

Слой определяет контракты (`IEventService`, `IBookingService`, `IEventRepository`, `IBookingRepository`), но не содержит конкретной реализации доступа к PostgreSQL.

### EventPlatform.Infrastructure

Слой реализации внешних технических зависимостей. Содержит:

- `AppDbContext` и конфигурации сущностей Entity Framework Core;
- реализации `EventRepository` и `BookingRepository`;
- PostgreSQL-провайдер Npgsql;
- миграции базы данных.

Регистрация `DbContext` и репозиториев выполняется методом `AddInfrastructure`.

### EventPlatform.Api

Внешний HTTP-слой приложения ASP.NET Core. Содержит контроллеры мероприятий, бронирований и проверки состояния, DTO-ответы, обработчик исключений и конфигурацию HTTP pipeline. Регистрация API выполняется методом `AddPresentation`.

При запуске API регистрирует Application и Infrastructure, применяет миграции базы данных и публикует HTTP endpoints.

## Pipeline

Администратор получает JWT в сервисе Users  
Администратор создает мероприятие с указанием срока проведения и числа мест в сервисе Events  
Пользователь регистрируется в сервисе Users `/api/auth/register`  
Пользователь получает JWT в сервисе Users  
Пользователь получает список мероприятий в Events  
Пользователь создает бронь на выбранное мероприятие в Bookings  
Bookings публикует сообщение в брокер в топик `bookings` о запросе бронирования  
Events подписан на топик `bookings` и получает сообщение-запрос бронирования  
Events проверяет число свободных мест на переданное мероприятие и дату проведения мероприятия  
Если все условия соблюдены Events публиекует сообщение об успешной резервации мест  
Bookings подписан на топик `events` и получает сообщение об успешной резервации мест на мероприятие  
Bookings переводит состояние брони из Pending в Confirmed. Это действие идемпотентно.  
При отрицательном сообщении из топика `events` Bookings переводит бронь в статус Rejected  

Пользователь может отменить бронь на любом этапе. Bookings публикует запрос на отмену мероприятия.  
Events получает это сообщение и проверяет дату проведения мероприятия. Нельзя отменить бронь на прошедшее мероприятие.  
Bookings переводит статус брони согласно сообщению от Events.  

Ранее BookingBackgroundService занимался задачами Events для перевода брони из статуса Pending в Confirmed или Rejected. Сейчас этим занимается Events, и Bookings не может сохранять Confirmed бронь в БД до обработки со стороны Events.

Нельзя сохранять Confirmed бронь т.к. условный email sender, подписанный на `BookingConfirmed` может отправить сообщение об успехе ещё до попытки списать места, которая может оказаться неудачной.  

## Users сервис

Users отвечает только за управление пользователями. Администратор может выполнять CRUD операции над пользователями в БД. Неавторизованный пользователь может зарегистрироваться и залогиниться (получить JWT).  
JWT подходит для всех микросервисов системы `EventPlatform` при условии указания общего secret и audience.  
БД этого сервиса хранится на отдельном postgres сервере. Название БД `users`.  

## Events сервис

Микросервис Events отвечает за обработку событий. Администратор может выполнять CRUD операции над ними. Неавторизованный пользователь может ознакомиться с мероприятиями, а для бронирования требуется авторизация.  
В зоне ответственности проверка времени проведения мероприятия, резервирование и освобождение мест. Микросервис публикует сообщения в своем топике и подписывается на топики других сервисов.  
**Публикует сообщения в топик `events` (продюсер):**

- `EventSeatsReservedMessage`
- `EventSeatsReservationFailedMessage`
- `EventSeatsReleasedMessage`
- `EventSeatsReleaseFailedMessage`

**Подписывается на топик `bookings` (консьюмер) обрабатывает сообщения:**

- `BookingCreateRequestedMessage`
- `BookingCancelRequestedMessage`  

Сообщения других типов пропускаются с записью в лог. Исключения при обработке сообщения заносятся в лог и подлежат отправке в DLQ.  
БД этого сервиса хранится на отдельном postgres сервере. Название БД `events`.

## Bookings сервис

Процесс бронирования начинается с сервиса Bookings. Пользователь запрашивает бронирование с указанием мероприятия и своего ИД. Микросервис публикует сообщения в своем топике и подписывается на топики других сервисов.  
**Публикует сообщения (продюсер):**

- `BookingCreateRequestedMessage`
- `BookingCancelRequestedMessage`

**Подписывается на топик `events` (консьюмер) обрабатывает сообщения**

- `EventSeatsReservedMessage`
- `EventSeatsReservationFailedMessage`
- `EventSeatsReleasedMessage`
- `EventSeatsReleaseFailedMessage`

Сообщения других типов пропускаются с записью в лог. Исключения при обработке сообщения заносятся в лог и подлежат отправке в DLQ.  

Из недостатков: сообщения в брокер поступают по порядку. Значит, сначала обработается запрос на бронирование и только потом на отмену.  
БД этого сервиса хранится на отдельном postgres сервере. Название БД `bookings`.

## Общая библиотека классов

Для соблюдения принципа DRY дублирующиеся классы и интерфейсы вынесены в общую библиотеку классов.  

## Контракты

Контракты сообщений и названия топиков описаны в общей библиотеке `EventPlatform.Contracts`.  
Структура сообщений содержит минимум полей, чтобы сократить трафик и увеличить скорость обмена сообщениями.  
В каждое сообщение добавляется заголовок `message-type`, который позволяет фильтровать сообщения и задает тип для десериализации.  
Ключом сообщения выступает ИД сущности для сохранения порядка обработки сообщений консьюмером.  
Названия групп консьюмеров для каждого сервиса вынесено в конфигурационный файл.  

## Брокер сообщений

В качестве брокера сообщений используется Apache Kafka с Pull моделью потребления.  
Для парадигмы at-least-once некоторые операции сервисолв выполнены идемпотентными.  
Кафка запускается в докере в комбинации с Zookeeper. Топики создаются автоматически по запросу консьюмеров. Получают сообщения продюсеров. Продюсер оформлен как синглтон и освобождается в методе `Dispose`.  

## Наблюдаемость (observability)

Мониторинг запускается одновременно с сервисами. Контейнеры находятся в общем docker compose.

Для сбора метрик используется **Prometheus** с PULL моделью. Он получает метрики обращаясь к сервисам по путям из раздела [Метрики](#метрики). Доступ к UI по адресу http://localhost:9090/targets

**Jaeger** собирает трейсы. PUSH модель, сервис сам отправляет данные по указанному адресу. Доступ к UI Jaeger по адресу http://localhost:16686

С отображением метрик в дашборде помогает **Grafana**. Она опрашивает Prometheus и из его данных строит графическое представление. Доступ к UI по адресу http://localhost:3000. Пользователь admin, пароль admin. Смену пароля можно пропустить кнопкой Skip. Файл [дашборда](/dashboard.json) лежит в репозитории.

### Дашборд

**Latency**

Благодаря вычислениям над метрикой `http_server_request_duration_seconds_bucket` отображается необходимый перцентиль задержек в обработке запросов. Это значит, что на графике будут отображены пики дольше заданного процента. На панели вынесены 3 графика для:

- p50 - медианное время выполнения запроса, чтобы видеть базу
- p95 - всплески задержек, стоит присмотреться
- p99 - запрос существенно выбивается из статистики, показывает болезненные деградации

В панели заданы thresholds для быстрой визуальной оценки задержки выполнения запросов. Значения границ задаются индивидуально для каждой системы.

- Зеленый в пределах нормы. В эту статистику могут попадать особые клиенты с тяжелыми запросами.
- За задержками в желтой зоне стоит наблюдать
- При попадании графика в красную зону, стоит обратить внимание на другие панели

**Throughput**

Метрика `http_server_request_duration_seconds_count` является постоянно растущим счетчиком, чтобы увидеть скорость приращения счетчика, применяется `rate()`. В результате отображается RPS. Позволяет оценить нагрузку на систему извне.

**GC**

В панели отображается количество сборок мусора в секунду. Для продакшена наиболее информативной является сборка GEN2, но для наглядности в работе отображается GEN0.

**Thread pool**

Стандартная метрика dotnet_thread_pool_thread_count_total показывает возникновение Thread starvation, когда количество свободных потоков подходит к пределу пула.

**Error rate**

Доля ошибок в процентах от общего трафика

**Вертикальное сканирование**

Выстроенные друг над другом панели Throughput, Latency, GC позволяют заметить корреляции в показаниях на временной шкале и сделать правильные выводы. Паттерны поведения графиков подскажут когда стоит обратиться к трейсам и логам.
